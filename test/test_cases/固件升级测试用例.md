# OTA 测试用例

实现：`module/ota_manager_service`、MCUboot。当前为签名镜像流程，不测试固件加密。

## 前置条件

准备当前版本和更高版本的 signed OTA 镜像、mcumgr 连接参数，并确认测试允许回滚和重复刷写。

## 验收概览

| 编号 | 测试内容 | 验收标准 | 结果 |
| --- | --- | --- | --- |
| OTA-001 | 镜像版本检查 | 镜像版本和签名状态可识别 | |
| OTA-002 | 正常升级 | 上传、切换、启动和确认成功 | |
| OTA-003 | 未确认回滚 | 新镜像未确认时回滚旧版本 | |
| OTA-004 | 中断恢复 | 上传或重启中断不会损坏当前镜像 | |
| OTA-005 | 非法镜像拒绝 | 签名错误或版本不允许时拒绝 | |

## 详细用例

### OTA-001 镜像版本检查

1. 使用发布的 `zephyr.signed.bin` 和 `zephyr.signed.hex`。
2. 用 `imgtool verify` 或发布工具检查镜像元数据。
3. 与测试台账中的版本、板卡和签名算法比对。

预期：镜像可验证，版本、硬件兼容性和签名信息正确。

### OTA-002 正常升级

1. 记录当前版本和设备身份。
2. 使用 mcumgr 上传升级镜像。
3. 设置 pending 并重启，确认设备运行新版本。
4. 执行 image confirm，再次重启。

预期：升级成功，设备身份和参数保持要求的状态，确认后不会回滚。

### OTA-003 未确认回滚

1. 上传可启动的新版本并重启。
2. 不执行 image confirm，再次重启。

预期：MCUboot 回滚到旧版本；设备仍可联网和维护。

### OTA-004 中断恢复

1. 上传过程中断开网络或停止客户端。
2. 等待设备恢复，再读取镜像状态。
3. 重新执行完整升级。

预期：当前可启动镜像不被破坏，重新上传可完成升级。

### OTA-005 非法镜像拒绝

1. 使用错误签名、损坏或不匹配板卡的镜像尝试升级。

预期：上传或启动阶段拒绝镜像，设备继续运行原版本。

## 缺陷证据

附镜像文件名及 SHA256、mcumgr 输出、重启时间、升级前后版本和 image list 结果。
